Run Tailscale in Rootless Mode

Installing Tailscale on a remote Linux server normally requires root (admin) access via sudo, /dev/net/tun, and systemd. On a shared server such as an HPC login node, a Slurm cluster, a Kubernetes pod, or an unprivileged Docker container, you usually have none of those.

Tailspace installs and supervises tailscaled in userspace networking mode with --tun=userspace-networking inside your home directory without root, so you can reach the server with SSH, VS Code Remote-SSH, or Jupyter from any device on your tailnet.

Install

One bash script, no sudo required

Run the installer on the remote server. It downloads Tailscale's official static binaries into ~/.tailspace, starts the supervisor, and prints a login URL plus an SSH command once the server joins your tailnet.

# Prints a login link and an SSH command once the server joins your tailnet
$curl -fsSL https://raw.githubusercontent.com/ttttonyhe/tailspace/main/tailspace | bash
Read CLI reference

Check shared cluster rules first. Tailspace keeps Tailscale running in the background, and Tailscale SSH skips the cluster's own two-factor check. Some clusters forbid one or both. Tailscale also expires device keys after 180 days by default, so disable key expiry in the admin console to keep the server online for good.

Supervision

Built to stay connected without systemd

Without root or systemd, Tailscale can't run as a system service. Tailspace runs a small user-level supervisor next to tailscaled to handle crashes, reboots, updates, and proxy drops:

  • SSH and local ports Turns on Tailscale SSH on port 22, forwards OpenSSH on port 2222 when the server runs OpenSSH, and lets you reach local ports such as Jupyter on 8888 or TensorBoard on 6006 over your tailnet. See the VS Code and Jupyter guide.
  • Crash and hang recovery Restarts tailscaled 5 seconds after a crash, checks state every 20 seconds so hangs restart after 3 missed checks, and restarts stuck connections once path probes confirm the network works.
  • Reboot recovery Adds a user cron job where a cron daemon runs, and a 0.9 ms shell check in your startup files everywhere else so the server rejoins on your next login.
  • Session-safe updates Checks for new Tailscale releases daily, waits up to 3 days while SSH or port-forwarded sessions are open, and rolls back if a release fails its 2-minute health check and 30-second soak.
  • Shared-host isolation Creates ~/.tailspace with mode 700, separates per-host state under state/HOSTNAME/ for shared NFS home directories, and keeps Tailscale's unauthenticated SOCKS5 and HTTP proxies off.
  • Clean stop states Stops and writes the exact reason to tailspace status after an expired key, a bad auth key, or 5 failed runs in a row, instead of retrying forever.
Failover

Automatic direct and HTTP proxy switching

Tailscale reads its proxy setting only at startup. When your server has an HTTP proxy, Tailspace monitors both the direct path and the proxy path using tailscale debug ts2021 probes and restarts tailscaled on whichever path works. Moving back to direct waits until active sessions close, up to 3 days. Read the HTTP proxy and DERP guide.

CLI

Everyday commands and requirements

Tailspace also puts a pre-wired tailscale command in ~/.local/bin that talks to your rootless socket with no extra flags:

tailspace status      # what it's doing, which path it's on, and why
tailspace stop        # stop Tailscale and keep it stopped across reboots
tailspace start       # start it again
tailspace restart     # restart Tailscale, even over Tailscale SSH
tailspace self-update # update Tailspace itself
tailspace uninstall   # log the server out and remove everything

Measured on a Kubernetes pod with 124 usable cores and 1,435 visible processes running Tailscale 1.104.7, capping GOMAXPROCS=8 cut Tailscale from 57 threads to 14 and probe CPU time from 57 ms to 15 ms. Requirements: Linux 3.2 or newer including CentOS 7, bash 4.2+, curl or wget, plus awk, flock, setsid, and timeout. See the full CLI and options reference.

FAQ

Frequently asked questions

Can I install and run Tailscale without root or sudo?

Yes. Tailspace downloads Tailscale's official static binaries into ~/.tailspace/bin and runs tailscaled --tun=userspace-networking. It never opens /dev/net/tun and doesn't ask for sudo, CAP_NET_ADMIN, or systemd.

Does Tailspace survive crashes and server reboots without systemd?

Yes. A user-level supervisor restarts tailscaled 5 seconds after a crash and checks it every 20 seconds so hangs restart after 3 missed checks. After a reboot, a user cron job starts Tailspace right away where cron runs, and a 0.9 ms shell check brings it back on your next login everywhere else.

Can I use VS Code Remote-SSH, Cursor, and Jupyter over rootless Tailscale?

Yes. Tailspace turns on Tailscale SSH on port 22 and forwards OpenSSH on port 2222 when the server runs OpenSSH, so VS Code Remote-SSH, Cursor, scp, and rsync connect to your server's tailnet name. Local web servers such as Jupyter on port 8888 or TensorBoard on port 6006 work at http://hostname:8888.

What happens if my server is behind an HTTP proxy or firewall?

Export https_proxy=http://HOST:PORT before installing. Tailspace saves that proxy, switches between the direct path and the proxy path when either fails, and switches back once direct access stays healthy. See the HTTP proxy failover guide.

Is Tailspace safe on a shared university or lab server?

Tailscale runs only as your user account, ~/.tailspace uses mode 700, and Tailscale's unauthenticated SOCKS5 and HTTP proxies stay off so other users on the host can't reach your tailnet. Pass keys with TS_AUTHKEY=file:/path/to/key so secrets never appear in /proc/*/cmdline.

How much CPU and memory does Tailspace use?

On a Kubernetes pod with 124 usable cores and 1,435 visible processes running Tailscale 1.104.7, Tailspace adds 0.9 ms to each new shell and uses 0.14% of one CPU core and 30 MB of memory at idle. Userspace networking moved about 10 Gbit/s in a local loopback test.
