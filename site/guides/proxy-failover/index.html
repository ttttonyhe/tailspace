Tailspace / HTTP proxy & failover

Tailscale behind HTTP proxies and direct/proxy failover

Tailscale reads its proxy setting only when tailscaled starts. On corporate networks, campus firewalls, or servers in mainland China whose HTTP proxy runs over a flaky VPN, a single proxy drop leaves standard Tailscale offline until someone restarts it by hand. Tailspace supervises both the direct path and the proxy path and switches when either breaks.

Setup

Install with an HTTP proxy

Export https_proxy before running the installer so curl can download Tailspace and Tailscale, and so Tailspace saves that proxy for the proxy path:

export https_proxy=http://127.0.0.1:7890
curl -fsSL https://raw.githubusercontent.com/ttttonyhe/tailspace/main/tailspace | bash

Change or clear the saved proxy at any time without reinstalling:

tailspace set --proxy http://127.0.0.1:7890
tailspace set --proxy none

Only http:// proxies work. Tailscale ignores ALL_PROXY and treats every proxy as HTTP, even if written as socks5://. Tailspace passes proxy settings via environment variables rather than command arguments so credentials stay out of /proc/*/cmdline.

Failover rules

How direct and proxy switching works

  • Grace windowsWhen Tailscale goes offline, the supervisor waits 4 minutes on the direct path to cover Tailscale's reconnect timers, or 1 minute on the proxy path, before probing.
  • Handshake probesTests each path with tailscale debug ts2021 against Tailscale's coordination server. If the active path fails and the other passes, it switches without waiting for sessions to close.
  • Stuck daemonIf the active path passes two consecutive probes while Tailscale stays offline, the supervisor restarts Tailscale on the same path.
  • Session-safe failbackAfter moving to the proxy path, Tailspace waits 15 minutes, then tests direct every 5 minutes. After two passing checks while online, it waits for sessions to close, up to 3 days, before moving back. If direct fails within 30 minutes, the 15-minute wait doubles up to 4 hours.
  • TLS ML-KEMSets GODEBUG=tlsmlkem=0 so middleboxes that drop post-quantum ML-KEM TLS handshakes don't block control connections; see tailscale#20777.
Relays

Speeding up slow DERP relays

When a server sits behind hard NAT or reaches the internet only over an HTTP proxy, traffic travels through a relay. Run tailspace status to see whether active peers show relay. Two Tailscale features bring a relay closer:

  • Custom DERP serverHelps on both paths. You don't need a domain name because derper --certmode manual --hostname IP --verify-clients generates its own certificate and prints the policy lines; run Tailscale on the same VPS so only your tailnet can use it.
  • Peer relaysIn Tailscale 1.86 and newer, one of your own devices can relay for the others over UDP. Helps only when the server can send UDP out directly, since HTTP proxies don't carry UDP.
FAQ

Frequently asked questions

Why can't Tailscale switch proxies on its own?

tailscaled reads https_proxy only once at startup. Tailspace probes both paths with tailscale debug ts2021 and restarts tailscaled in the working environment whenever the active path breaks.

Does Tailscale support SOCKS5 proxies via ALL_PROXY?

No. Tailscale ignores ALL_PROXY and parses every proxy as HTTP. Expose an HTTP proxy port, such as Clash or Mihomo's mixed port, and pass it as http://HOST:PORT.

Will failing back to the direct path kill my open SSH session?

No. Moving back to direct waits while Tailspace sees open SSH sessions, forwarded connections to 127.0.0.1 or ::1, or LocalAPI clients, up to 3 days in all. Tailspace excludes tailscaled's own loopback proxy sockets from that count so a local proxy never blocks failback forever.
