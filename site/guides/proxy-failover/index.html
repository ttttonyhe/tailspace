Tailspace / HTTP proxy & failover

Tailscale behind HTTP proxies and direct/proxy failover

Tailscale reads its proxy setting only when tailscaled starts. On corporate networks, campus firewalls, or servers in mainland China whose HTTP proxy runs over a flaky VPN, a single proxy drop leaves standard Tailscale offline until someone restarts it by hand. Tailspace supervises both the direct path and the proxy path and switches when either breaks.

Install with an HTTP proxy

Export https_proxy before running the installer so curl can download Tailspace and Tailscale, and so Tailspace saves that proxy for the proxy path:

export https_proxy=http://127.0.0.1:7890
curl -fsSL https://raw.githubusercontent.com/ttttonyhe/tailspace/main/tailspace | bash

Change or clear the saved proxy at any time without reinstalling:

tailspace set --proxy http://127.0.0.1:7890
tailspace set --proxy none

Only http:// proxies work. Tailscale ignores ALL_PROXY and treats every proxy as HTTP, even if written as socks5://. Tailspace passes proxy settings via environment variables rather than command arguments so credentials stay out of /proc/*/cmdline.

How direct and proxy failover works

  • Grace windows. When Tailscale goes offline, the supervisor waits 4 minutes on the direct path to cover Tailscale's own reconnect timers, or 1 minute on the proxy path, before probing.
  • Real handshake probes. Tailspace tests each path by opening a fresh Noise handshake to Tailscale's coordination server with tailscale debug ts2021. If the active path fails and the backup path passes, it switches without waiting for sessions to close.
  • Stuck-daemon detection. If the active path passes two consecutive probes while Tailscale stays offline, Tailscale is stuck and the supervisor restarts it on the same path.
  • Session-safe failback with flap backoff. After switching to the proxy path, Tailspace waits 15 minutes, then tests the direct path every 5 minutes. Once two consecutive tests pass while online, it waits for active Tailscale sessions to close, for 3 days at most, before moving back to direct. If direct fails again within 30 minutes, that 15-minute wait doubles, up to 4 hours.
  • TLS ML-KEM compatibility. Tailspace sets GODEBUG=tlsmlkem=0 so middleboxes that drop post-quantum ML-KEM TLS handshakes don't block control connections; see tailscale#20777. Tailscale's own encryption still protects all traffic.

Speeding up slow DERP relays

When a server sits behind hard NAT or reaches the internet only over an HTTP proxy, traffic travels through a relay. Run tailspace status to see whether active devices hit a DERP relay, shown as relay. Two Tailscale features bring a relay closer:

  • Self-hosted custom DERP server. Helps on both the direct path and the HTTP proxy path. You don't need a domain name because derper --certmode manual --hostname IP --verify-clients makes its own certificate and prints the policy lines. Run Tailscale on the same machine so --verify-clients admits only your tailnet.
  • Peer relays. Available in Tailscale 1.86 and newer, peer relays let one of your own devices relay for the others. They use UDP, which HTTP proxies don't carry, so they help only when the server can send UDP out directly.

Frequently asked questions

Why can't Tailscale switch proxies on its own?

tailscaled reads https_proxy only once at startup. Tailspace probes both paths with tailscale debug ts2021 and restarts tailscaled in the working environment whenever the active path breaks.

Does Tailscale support SOCKS5 proxies via ALL_PROXY?

No. Tailscale ignores ALL_PROXY and parses every proxy as HTTP. Expose an HTTP proxy port, such as Clash or Mihomo's mixed port, and pass it as http://HOST:PORT.

Will failing back to the direct path kill my open SSH session?

No. Moving back to direct waits while Tailspace sees open SSH sessions, forwarded connections to 127.0.0.1 or ::1, or LocalAPI clients, up to 3 days in all. Tailspace excludes tailscaled's own loopback proxy sockets from that count so a local proxy never blocks failback forever.
