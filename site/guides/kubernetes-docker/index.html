Tailspace / Kubernetes & Docker

Tailscale in Kubernetes pods and unprivileged Docker containers

Locked-down GPU pods, managed Kubernetes dev environments, and unprivileged Docker containers strip out CAP_NET_ADMIN, hide /dev/net/tun, and run without systemd or cron. Tailspace installs into your home directory with one command and gives you Tailscale SSH, VS Code Remote-SSH, and localhost port access without changing pod specs or container privileges.

Zero container privileges required

Standard Tailscale container guides ask for CAP_NET_ADMIN and a host mount for /dev/net/tun. When you don't control the cluster SecurityContext, Tailspace skips kernel networking by running tailscaled --tun=userspace-networking:

curl -fsSL https://raw.githubusercontent.com/ttttonyhe/tailspace/main/tailspace | bash

For non-interactive pod startup scripts or recreated pods, mount a reusable auth key as a 0600 Kubernetes Secret and pass it through TS_AUTHKEY:

curl -fsSL https://raw.githubusercontent.com/ttttonyhe/tailspace/main/tailspace | \
  TS_AUTHKEY=file:/var/run/secrets/tailscale/authkey bash -s -- install --hostname gpu-pod-01

How Tailspace handles container environments

  • UDP GSO off in containers. On some container virtual NICs, UDP GSO batches packets in a way that cripples throughput; see tailscale#20858. Tailspace detects container cgroup namespaces and turns UDP GSO off.
  • No systemd, no init, no cron required. Containers without an init process leave zombies un-reaped, so Tailspace reads process state in /proc and treats zombies as gone. It also skips adding a crontab entry when no cron daemon runs on the container's own root filesystem, even under hostPID: true.
  • Safe with shared host PID namespaces. Process detection never runs ps or pgrep. The supervisor identifies its own tailscaled and lock holders through /proc/PID/fd and --statedir, so other pods on the same node are never touched.
  • Pod restart detection. Tailspace records each container's root overlay identity alongside the kernel boot ID. If a pod restarts with the same hostname and persistent $HOME volume, Tailspace treats it as a reboot and clears earlier give-ups on your next kubectl exec shell.
  • Capped Go threads on large worker nodes. A container on a 124-core Kubernetes worker normally inherits 124 usable CPUs. Tailspace caps GOMAXPROCS=8, cutting Tailscale from 57 threads to 14 and probe CPU time from 57 ms to 15 ms.

Skip kubectl port-forward for Jupyter and dev servers

In userspace mode, Tailscale forwards every port on the pod's tailnet IP to 127.0.0.1 inside the pod, apart from port 22 for Tailscale SSH and port 2222 when OpenSSH runs. Start Jupyter on 8888, TensorBoard on 6006, or a local API on 8000, and open http://gpu-pod-01:8888 from your laptop browser.

Frequently asked questions

Does Tailspace need CAP_NET_ADMIN or /dev/net/tun in Kubernetes or Docker?

No. Tailspace launches tailscaled --tun=userspace-networking, so it never accesses /dev/net/tun and needs no Linux capabilities or privileged container settings.

How does Tailspace recover when a container has no systemd or cron?

Tailspace adds a 0.9 ms background shell check to your startup files, such as ~/.bashrc and ~/.zshrc. After a pod restarts, the next kubectl exec or shell login starts the supervisor and tailscaled again.

What if a Kubernetes Deployment assigns a new pod hostname on recreate?

Tailspace names each state directory after the container's OS hostname under state/HOSTNAME/, so a pod recreated with a new hostname counts as a new server. Use a StatefulSet or fixed spec.hostname to keep that state directory across recreates, or run tailspace install again with a reusable auth key.
